
# TP、FP、FN、TN 详解

TP、FP、FN、TN 是二分类评估里最基础的四个概念，来自**混淆矩阵（Confusion Matrix）**。理解它们的关键在于拆开名字：

- **第一个词（True / False）**：表示模型这次预测**对不对**
- **第二个词（Positive / Negative）**：表示模型**预测的类别是什么**（正类还是负类）

判断顺序：先看模型预测成了什么（第二个词），再看预测对不对（第一个词）。

## 逐个解释

**TP（True Positive，真正例）**
模型预测为**正类**，且实际**确实是正类**。预测正确。
例：模型判断"这两个地址是同一实体的存/取款对"，实际上它们确实是一对 → TP。

**FP（False Positive，假正例 / 误报）**
模型预测为**正类**，但实际是**负类**。预测错误。
"多报"了——把不相关的东西认成了正类。
例：模型说两个地址是关联的，实际它们毫无关系 → FP。

**FN（False Negative，假负例 / 漏报）**
模型预测为**负类**，但实际是**正类**。预测错误。
"漏掉"了——真正的正类没被识别出来。
例：两个地址其实是一对，但模型判成了不相关 → FN。

**TN（True Negative，真负例）**
模型预测为**负类**，且实际**确实是负类**。预测正确。
例：两个不相关的地址，模型也判成不相关 → TN。

## 记忆技巧

把 "Positive/Negative" 理解成模型的**主张**，把 "True/False" 理解成这个主张的**真假**：

- True → 模型说对了（TP、TN 都是对的）
- False → 模型说错了（FP、FN 都是错的）
- **FP 和 FN 是两种不同的错误**：FP 是"宁可错杀"（误报），FN 是"错放走"（漏报），二者往往此消彼长，需要根据业务权衡。

## 由它们衍生的常用指标

| 指标 | 公式 | 含义 |
|---|---|---|
| Precision（精确率） | TP / (TP + FP) | 预测的所有正类里有多少是对的 |
| Recall（召回率 / TPR） | TP / (TP + FN) | 真实正类里有多少被找出来了 |
| FPR（假正率） | FP / (FP + TN) | 事实为负类里有多少被误报（ROC 横轴） |
| F1 | 2·P·R / (P + R) | 精确率和召回率的调和平均 |

## 汇总表

| 缩写 | 全称 | 中文 | 预测值 | 实际值 | 预测对错 | 通俗理解 |
|---|---|---|---|---|---|---|
| **TP** | True Positive | 真正例 | 正 | 正 | ✅ 对 | 正确命中 |
| **FP** | False Positive | 假正例 | 正 | 负 | ❌ 错 | 误报（多报了） |
| **FN** | False Negative | 假负例 | 负 | 正 | ❌ 错 | 漏报（漏掉了） |
| **TN** | True Negative | 真负例 | 负 | 负 | ✅ 对 | 正确排除 |

标准混淆矩阵布局（行=实际，列=预测）：

| | 预测为正 | 预测为负 |
|---|---|---|
| **实际为正** | TP | FN |
| **实际为负** | FP | TN |

# AUPRC / AUC 在类别不平衡场景下的对应（以 TC Linkage 为例）

用一组具体数字来看。这里最能说明问题的就是**类别极度不平衡**——候选对里真正关联的对是极少数。

## 设定一个贴近现实的测试集

假设从存/取款地址里生成了一批候选对来评估，共 **100 万个候选对**：

- 真实关联对（正样本 P）：**1,000 个**
- 无关对（负样本 N）：**999,000 个**
- 正样本占比（prevalence）：1000 / 1,000,000 = **0.1%**

这个 0.1% 是关键，后面所有"错觉"都从这里来。

## 在某个阈值下算一次混淆矩阵

假设模型在某阈值下表现"看起来不错"：

| | 预测为关联 | 预测为无关 |
|---|---|---|
| **实际关联** | TP = 800 | FN = 200 |
| **实际无关** | FP = 9,000 | TN = 990,000 |

拿这四个数算指标：

- **Recall（召回率）= TP/(TP+FN) = 800/1000 = 0.80** —— 1000 对真关联找回了 800，不错
- **FPR（假正率）= FP/(FP+TN) = 9000/999000 ≈ 0.009** —— 只有 0.9%，看着极小
- **Precision（精确率）= TP/(TP+FP) = 800/9800 ≈ 0.082** —— 只有 **8.2%**！

## 关键矛盾：ROC 说"很好"，PR 说"很差"

**ROC 曲线**看的是 (FPR, TPR) = (0.009, 0.80)，几乎贴着左上角，AUC 会算得很高，比如 **0.98**，一片祥和。

问题出在哪？**FPR 的分母是 99.9 万个负样本**，9000 个误报被这个巨大的分母一稀释，就显得微不足道。ROC 完全感受不到你误报了 9000 个。

**PR 曲线**看的是 (Recall, Precision) = (0.80, 0.082)。翻译成人话：

> 模型报给分析师 9,800 个"关联对"，其中只有 800 个是真的，**剩下 9,000 个（92%）是垃圾**。分析师每核实 12 个才碰到 1 个真的。

这才是实际落地时的痛感。AUC 0.98 骗了你，AUPRC 才诚实。

## 为什么 AUPRC 在这种场景是主指标

两个 baseline 对比记住就行：

| 指标 | 随机分类器的 baseline | 说明 |
|---|---|---|
| **AUC** | **恒为 0.5**（和不平衡无关） | 所以 0.98 看着唬人，但没告诉你误报代价 |
| **AUPRC** | **等于正样本占比 = 0.001** | 极度不平衡时

## 1. 任务与打分对象

MixBroker 做的是**边分类 / 链接预测（Link Prediction）**：判断两个以太坊地址 `(nodeid1, nodeid2)` 是否属于同一实体。因此每一条测试边都有：

- 真实标签 `edge_label` ∈ {0, 1}（1 = 关联，0 = 无关联）
- 模型预测的关联概率 ∈ [0, 1]

评分就是把这两者**逐条对比**后统计出来的。数据集正负样本 1:1 平衡（各 103 条边），这一点在解读 Accuracy 时很关键。

---

## 2. 从模型输出到「预测标签」

打分前有一个关键的**离散化步骤**（`main.py:31-37`）：

```python
z   = model.encode(data.x, data.edge_index)                      # 图编码 → 节点嵌入
out = model.decode(z, data.edge_label_index).view(-1).sigmoid()  # 边 logit → sigmoid → 概率
out_np = out.cpu().numpy()
label_pred = np.where(out_np > 0.75, 1, 0)                       # 阈值 0.75 二值化
```

- `out_np`：每条边的**关联概率**（连续值，用于算 AUC）
- `label_pred`：**硬预测**，`概率 > 0.75` 才判为「关联」

> ⚠️ **阈值 0.75 是硬编码的**，不是常见的 0.5。这个偏高的阈值倾向「宁可漏报也少误报」，会直接影响下面除 AUC 外的所有指标。

---

## 3. 混淆矩阵（所有指标的基础）

`mytest()` 手写遍历每条测试边，累计四个计数（`main.py:39-48`）：

|            | 预测=关联 (1) | 预测=无关联 (0) |
|------------|:-------------:|:---------------:|
| **真实=关联 (1)** | TP（命中）    | FN（漏报）      |
| **真实=无关联 (0)** | FP（误报）    | TN（正确排除）  |

| 计数 | 全称 | 含义 |
|------|------|------|
| **TP** | True Positive  | 真实关联，且预测关联 |
| **FP** | False Positive | 真实无关联，却预测关联（误报） |
| **FN** | False Negative | 真实关联，却预测无关联（漏报） |
| **TN** | True Negative  | 真实无关联，且预测无关联 |

后续 6 项指标（Accuracy / Precision / Recall / F1 / FPR / FNR）都由这四个数算出；只有 AUC 直接基于连续概率 `out_np`。

---

## 4. 七项评分指标详解（意义 / 计算 / 优缺点）

### 4.1 Accuracy 准确率

- **计算方法**：`(TP + TN) / (TP + FP + FN + TN)`
  代码：`sm.accuracy_score(label_test, label_pred)`（`main.py:53`）
- **意义**：所有测试边中，模型判断正确的比例；最直观的「整体对不对」指标。
- **优点**：
  - 直观易懂，单个数字概括整体表现。
  - 在本任务中**正负样本 1:1 平衡**，因此 Accuracy 有实际参考价值（不像不平衡场景那样失真）。
- **缺点**：
  - 对类别不平衡极其敏感。若负样本占 99%，一个「全判无关联」的模型 Accuracy 也有 99%，却毫无用处。
  - 把误报和漏报**等价看待**，无法区分两类错误的不同代价。
  - 依赖固定阈值 0.75，阈值一变数值就变。

### 4.2 Precision 精确率

- **计算方法**：`TP / (TP + FP)`
  代码：`sm.precision_score(label_test, label_pred)`（`main.py:54`）
- **意义**：模型判为「关联」的边里，有多少是真的关联 → **误报控制能力**。
- **优点**：
  - 直接回答「模型说两人是同一人，可信度多高」，在去匿名化 / 取证场景极其重要——**误指两个无关地址属于同一人，代价很高**（可能牵连无辜）。
  - 不受 TN 影响，对大量真负例不敏感。
- **缺点**：
  - 只看「报出来的准不准」，完全不管**漏掉了多少**（不含 FN）。模型只报最有把握的 1 条且报对，Precision 就是 100%，但可能漏掉了 99% 的关联。
  - 必须与 Recall 联合看，单独一个 Precision 可以被「保守预测」刷高。
  - 依赖阈值 0.75；阈值越高 Precision 通常越高。

### 4.3 Recall 召回率

- **计算方法**：`TP / (TP + FN)`
  代码：`sm.recall_score(label_test, label_pred)`（`main.py:55`）
- **意义**：所有真实关联的边里，被模型成功抓到的比例 → **漏报控制能力 / 攻击覆盖面**。
- **优点**：
  - 直接衡量「去匿名化攻击能覆盖多少真实关联」，攻击方视角下最关心的指标之一。
  - 不受 TN 影响。
- **缺点**：
  - 完全不管**误报**（不含 FP）。一个「全判关联」的模型 Recall = 100%，但 Precision 极低、毫无价值。
  - 必须与 Precision 联合看；单独刷高 Recall 很容易（放宽阈值即可）。
  - 依赖阈值 0.75；阈值越低 Recall 通常越高。

### 4.4 F1 分数

- **计算方法**：`2 · Precision · Recall / (Precision + Recall)`（精确率与召回率的**调和平均**）
  代码：`sm.f1_score(label_test, label_pred)`（`main.py:56`）
- **意义**：在「误报」与「漏报」之间取平衡的综合指标。**本项目的主指标**——每折就是按测试集 F1 最高来选最优 epoch（`main.py:131`）。
- **优点**：
  - 用**调和平均**而非算术平均，任一项（P 或 R）偏低都会显著拉低 F1，迫使模型两头都要好，难以靠单边刷分。
  - 在正负平衡 / 关注正类的场景下，比 Accuracy 更能反映真实能力。
- **缺点**：
  - 完全**忽略 TN**，不衡量对真负例的排除能力。
  - 默认认为 Precision 和 Recall 同等重要（β=1）；若实际业务中误报和漏报代价不同，F1 并不能体现这种偏好（需改用 Fβ）。
  - 依赖固定阈值 0.75，是「模型 + 该阈值」的联合表现，而非模型本身的上限。

### 4.5 FPR 误报率（False Positive Rate）

- **计算方法**：`FP / (FP + TN)`
  代码：手写 `FPR = FP / (FP + TN)`（`main.py:51`）
- **意义**：所有真实**无关联**的边中，被错判为关联的比例；是 ROC 曲线的横轴。越低越好。
- **优点**：
  - 从「负样本」角度补充刻画误报，是 Precision 之外的另一个误报视角。
  - 是 ROC / AUC 的构成维度，便于跨阈值分析。
- **缺点**：
  - 分母是 FP+TN，在负样本极多时 FPR 会被大量 TN「稀释」得很小，看起来漂亮但绝对误报数可能不少。
  - 单独看无意义，需与 TPR（=Recall）配合（即 ROC 曲线）。
  - 依赖阈值 0.75。

### 4.6 FNR 漏报率（False Negative Rate）

- **计算方法**：`FN / (TP + FN)`
  代码：手写 `FNR = FN / (TP + FN)`（`main.py:52`）
- **意义**：所有真实**关联**的边中，被漏掉的比例。等价于 `1 − Recall`。越低越好。
- **优点**：
  - 直接量化「攻击漏掉了多少真实关联」，比 Recall 更直观地表达「失误」。
  - 与 Recall 冗余但互补，报告中并列可读性更好。
- **缺点**：
  - 与 Recall 完全等价（`FNR = 1 − Recall`），信息上不提供新内容，同时报两个略显冗余。
  - 完全不管误报（不含 FP）。
  - 依赖阈值 0.75。

### 4.7 AUC（ROC 曲线下面积）

- **计算方法**：ROC 曲线（横轴 FPR、纵轴 TPR）下的面积
  代码：`sm.roc_auc_score(label_test, out_np)`（`main.py:57`）
  **注意传入的是连续概率 `out_np`，而非二值化后的 `label_pred`。**
- **意义**：衡量模型把「正样本排在负样本前面」的能力，即随机取一正一负两条边、模型给正边更高分的概率。**阈值无关**——反映模型本身的区分能力上限。
- **优点**：
  - **不依赖 0.75 阈值**，评估的是模型的排序 / 区分能力本身，不受二值化策略影响。
  - 对类别不平衡相对稳健，可跨数据集 / 跨阈值横向比较。
  - 概率意义明确（= 正样本得分高于负样本的概率）。
- **缺点**：
  - 是「全阈值平均」的乐观视角，可能掩盖你实际部署的那个阈值（0.75）下的真实表现——AUC 高不代表 0.75 阈值下 F1 也高。
  - 在极端不平衡场景下，AUC（基于 ROC）会显得偏乐观，此时 PR-AUC 更合适。
  - 不直接告诉你「该用哪个阈值」，也不反映误报 / 漏报的业务代价。

## 5. 指标间的关系

- `FNR = 1 − Recall`（二者等价，互为补数）。
- `Precision / Recall / F1 / FPR / FNR / Accuracy` 全部建立在 **0.75 阈值**切出的 `label_pred` 上——它们衡量的是「模型 + 这个特定阈值」的**联合表现**。
- **只有 AUC 是阈值无关的**，衡量的是模型本身的好坏。
- 便于记忆的一句话：**前六项看「模型 + 阈值配合得好不好」，AUC 看「模型底子好不好」**。
- 看结果时最该盯的两个数：**F1（选模主指标）** 与 **AUC（模型本质区分力）**。

## 6. 模型选择与聚合（单折 → 10 折）

**单折内选模**（`main.py:131-139`）：每折训练 100 epoch，`epoch > 10` 之后，取**测试集 F1 最高**那个 epoch 的全部 7 项指标作为该折成绩。

> ⚠️ **方法学提示**：此处直接在**测试折**上按 F1 选最优 epoch（没有独立验证集），存在一定「看着答案选模型」的乐观偏差。加上每折测试边仅约 20 条，单折指标波动很大（pipeline §9.1 中 F1 从 0.70 到 0.95）。

**10 折聚合**（`main.py:152-157`）：对 10 折的每项指标取 **mean ± std**，作为最终报告值。

**解读**：在更大数据集上，Precision(0.751) 明显高于 Recall(0.673)、FNR 高达 0.327——说明 0.75 这个高阈值让模型**偏保守、漏报偏多**。这正好印证了「除 AUC 外的指标都强依赖阈值」这一点：AUC 仍有 0.862（模型区分力不差），但固定 0.75 阈值下 F1 被漏报拖到 0.708。

---

## 8. 小结

一句话概括 MixBroker 的评分标准：

> 先用 GraphSAGE 算出每条地址对的**关联概率**，以 **0.75** 为阈值二值化后统计 **TP/FP/FN/TN**，导出 **Accuracy、Precision、Recall、F1、FPR、FNR** 六项阈值相关指标 + 一项阈值无关的 **AUC**；每折按 **F1** 选最优 epoch，再对 **10 折**取 **mean ± std**。

- **F1**：选模主指标，平衡误报与漏报。
- **AUC**：评估模型本质区分力，阈值无关，跨数据集可比。
- 其余指标各有侧重（Precision→误报、Recall/FNR→漏报、FPR→负样本误报、Accuracy→整体），但都受硬编码阈值 0.75 影响，需结合阈值一起解读。

## 9. 实验设定的根本局限：1:1 平衡采样 vs 真实场景

MixBroker 的评估集只有 **103 个正样本 + 按 1:1 随机采样的 103 个负样本**（共 206 条边）。这个设定与真实的 TC 关联性预测场景存在**量级上的偏离**，导致上面报告的漂亮指标在落地时会严重失真。下面把「缺点」和「被这套评估掩盖、从而没有被反映出来的问题」分开整理。

### 9.1 问题的根源：采样空间的量级鸿沟

| 维度 | 实验设定 | 真实使用场景 |
|------|----------|--------------|
| 待判定对象 | 预先给定的 206 条边 | **所有存款地址 × 所有取款地址**之间的关联关系 |
| 候选对规模 | 206 | 数据集 68,419 个地址，全配对 C(68419,2) ≈ **2.3×10⁹**；即便只取 deposit×withdraw 也在 **10⁸~10⁹** 量级 |
| 正样本占比（prevalence） | **50%** | 真实关联对可能仅数千个 → 占比约 **10⁻⁶ 或更低** |
| 负样本来源 | 从全空间随机抽 103 个 | 全部未关联对，其中含大量「难负样本」 |

**核心矛盾**：模型在「50% 都是正样本」的世界里被训练和评估，却要部署到「一百万对里才有一对是真的」的世界。分布错配（distribution shift）使得平衡集上的指标几乎无法外推。

### 9.2 缺点一：负样本「太好认」，Precision 被严重高估

随机抽取的 103 个负样本，两个地址大概率行为特征差异巨大、在图上毫不相干 → **极易分对**。而真实场景的难点恰恰是**难负样本（hard negatives）**：

- 同一个池、金额相同、存取时间接近的地址对；
- 特征高度相似但并不属于同一实体。

这些正是模型最容易产生 FP（误报）的地方，而**随机采样几乎抽不到它们**。后果：

- 报告的 Precision / F1 是在「简单负样本」上刷出来的，真实场景中面对难负样本会明显下降；
- 论文 0.87 / 复现 0.75 的 Precision，**不代表**在全量候选对上的可信度。

### 9.3 缺点二：阈值相关指标在真实分布下集体失真

用一个贴近现实的数字说明（详见本文档前面「AUPRC / AUC」一节）。假设真实测试集 100 万个候选对、其中 1000 个真关联：

| 指标 | 1:1 平衡集（实验报告） | 真实极度不平衡场景 | 失真原因 |
|------|----------------------|-------------------|----------|
| **Accuracy** | 有意义（≈0.85） | **失效**：全判「无关联」即可达 99.9% | 被海量 TN 支配 |
| **FPR** | 0.07~0.14 | 看着仍极小（如 0.9%） | 分母 FP+TN 里 TN 是天文数字，把误报稀释掉 |
| **Precision** | 0.75~0.87 | **崩塌**：FPR 0.9% × 99.9 万负样本 = 9000 个 FP ≫ TP，Precision 可能只有 8% | 负样本基数爆炸 |
| **AUC(ROC)** | 0.86~0.88 | 依旧虚高（可达 0.98） | ROC 基于 FPR/TPR，对不平衡不敏感 |
| **AUPRC** | 未报告 | 才是诚实指标，随机 baseline 仅 = prevalence ≈ 0.001 | 直面「报出来的有多少是真的」 |

**关键点**：实验里**只报 ROC-AUC、不报 AUPRC**，而 AUC 恰恰是这套指标里唯一「对不平衡免疫」的——于是它在平衡集和真实集上都好看，制造了「模型很强」的错觉，却**掩盖了 Precision 在真实分布下会崩塌**的事实。

### 9.4 缺点三：0.75 阈值不可迁移

阈值 0.75 是在 **1:1 平衡分布**上定的。到了极度不平衡场景，预测得分的分布会整体平移，这个阈值完全不再适用——要保住 Precision 往往需要极高的阈值，而那会让 Recall 崩掉。实验**没有反映「部署时如何标定阈值」**这个真实落地的核心难题。

### 9.5 缺点四：样本量过小 + 选择偏差

- 每折测试集仅约 20 条边，单条边错判就让指标跳动约 5%，`std` 很大（论文 F1 的 std 达 0.08），统计上不可靠。
- 103 个正样本全部来自 **ENS 域名转移泄漏**——这只覆盖「既用 ENS、又在 TC 存取」的特定人群，存在明显**选择偏差**，其关联模式未必能代表全体 TC 用户。

### 9.6 被这套评估「掩盖」、完全没有反映出来的问题

1. **候选生成（candidate generation / blocking）被跳过**：真实系统面对 10⁹ 量级候选对，不可能全量两两打分，必须先有一套召回/blocking 机制把候选缩小到可处理规模。实验直接给定 206 条边，**回避了整个系统里最难、最影响最终 Precision 的一环**。
2. **排序质量未被评估**：真实用途更接近「输出 Top-K 最可能的关联对交人工核实」，应使用 **Precision@K、Recall@K、MRR、AUPRC** 等排序/不平衡指标，而非固定阈值下的 P/R/F1。实验的评估范式与真实用法不匹配。
3. **人工核实成本不可见**：平衡集上看不到「分析师要筛掉多少垃圾才碰到一个真关联」。真实场景下 Precision 8% 意味着**每核实 ~12 个才命中 1 个**——这才是落地痛感，指标里完全没体现。
4. **类别不平衡下的训练/校准缺失**：模型只在 1:1 上训练，从未见过真实比例，输出概率在真实分布上是 miscalibrated 的，0.75 这类阈值语义失效。
5. **时间外推能力未验证**：10 折是按边**随机**划分，而非按时间切分。真实任务是用历史预测未来关联，随机划分可能造成信息泄漏，高估了对未来数据的泛化能力。

### 9.7 结论

MixBroker 报告的 F1≈0.85 / AUC≈0.88 是在一个**正样本占 50%、负样本随机且简单、样本量仅两百条**的「玩具分布」上得到的。它证明了「图特征学习原理上能区分关联/非关联」，但：

> **它没有回答真实场景真正关心的问题**——在 10⁹ 量级、正样本占百万分之一、且充满难负样本的候选空间里，模型能否以人工可接受的 Precision 召回足够多的真实关联。

要让评估贴近现实，至少应：① 按真实（或至少显著不平衡，如 1:100、1:1000）的比例采样负样本，并纳入难负样本；② 用 **AUPRC、Precision@K、Recall@K** 替代/补充固定阈值的 P/R/F1；③ 显式建模候选生成阶段；④ 采用按时间的训练/测试划分。
